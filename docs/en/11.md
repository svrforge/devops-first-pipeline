# Day 11 — Write a test that can fail

[All days](README.md) · [Animated classroom](../../academy/index.html#day=11)

## The idea

A useful test checks behavior and fails when that behavior breaks. The HTTP tests start a server on an available local port and make real requests. They do not call a public API or depend on your already-running local service. Determinism makes failures easier to trust.

## A familiar example

A smoke detector must react to smoke, not merely confirm that its casing exists.

## Walk through it

### 1. Arrange

Create the temporary server and test input.

### 2. Act

Send the HTTP request for the behavior being checked.

### 3. Assert

Compare status or body to the intended contract.

### 4. Clean

Stop the temporary server so later tests do not inherit leaked processes.

## Try it yourself

Run from the repository root. Read comments and prerequisites first.

```bash
python -m unittest discover -s tests -v
```

## Expected evidence

Find test_unknown_path and explain how it would fail if the app returned 200 for every path.

## Break, diagnose, recover

Change the 404 route behavior in a temporary branch. Confirm the correct test fails, then restore it.

## Check your understanding

Which test is stronger?

1. A test that always passes
2. A test that detects an incorrect response
3. A test that prints OK
